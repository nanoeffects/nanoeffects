# Политики

> **[Уровень B](README.md#виды-проектов)**: SPA с async UI. Сначала прочитайте: [Руководство](guide.md#1-создание-шины-событий).

В SPA обработчики накладываются друг на друга: поиск по мере набора, повторная отправка, уход со страницы. **Политика** оборачивает обработчик и решает, что делать с наложением.

Начните с `latest`. Остальные политики — в таблице и разделах ниже.

## `latest`: прерывание предыдущего запуска

```js
import { createBus } from "nanoeffects";
import { latest } from "nanoeffects/policies";

const bus = createBus();

// latest — новый запуск прерывает старый
bus.on(
  "search",
  latest(async (query, { signal }) => {
    // signal — позволяет latest отменить этот запрос, а не только отбросить его результат
    await api.search(query, { signal });
  }),
);
```

Передайте `signal` в `fetch` (и подобные вызовы), чтобы запрос отменялся. Чтобы не передавать его вообще, привяжите сигнал один раз: с `signalFetch(ctx, url)` запрос останавливается вместе с обработчиком, и забыть нечего ([Сохранение сигнала в обработчике](pass-the-signal.md#привязка-сигнала-один-раз)).

## Таблица политик

Каждая политика принимает `key` в параметрах (см. [`key`: разделение state по ключу](#key-разделение-state-по-ключу)).

| Политика | Накладывающиеся вызовы |
| -------- | ---------------------- |
| `latest(fn)` | предыдущий запуск прерван, результат отброшен |
| `leading(fn)` | новые вызовы отбрасываются, пока идёт запуск |
| `debounce(ms, fn, options?)` | запуск после `ms` тишины |
| `throttle(ms, fn, options?)` | не больше одного запуска за `ms` |
| `queue(fn, options?)` | один за другим, по порядку |
| `dedupe(fn, options?)` | вызовы с одним ключом делят идущий запуск |
| `distinct(fn, options?)` | вызов с тем же payload, что и последний, пропускается |
| `rateLimit(limit, ms, fn, options?)` | не больше `limit` запусков за `ms`, остальные ждут |
| `batch(ms, fn, options?)` | payload одного окна попадают в `fn` одним массивом |

## Справочник политик

По одной записи на политику: что она делает и ссылка на полный рецепт.

### `latest`

Новый вызов прерывает старый и отбрасывает его результат.

Сигнатура: `latest(fn, options?)`.

Подробнее: [`latest`: прерывание предыдущего запуска](#latest-прерывание-предыдущего-запуска).

### `leading`

Новые вызовы отбрасываются, пока идёт запуск.

Сигнатура: `leading(fn, options?)`.

Подробнее: [Защита от повторной отправки](prevent-double-submit.md).

### `debounce`

Запускается после `ms` тишины.

Сигнатура: `debounce(ms, fn, options?)`.

Подробнее: [Настройка debounce и throttle](#настройка-debounce-и-throttle).

### `throttle`

Не больше одного запуска в течение `ms`.

Сигнатура: `throttle(ms, fn, options?)`.

Подробнее: [Настройка debounce и throttle](#настройка-debounce-и-throttle).

### `queue`

Формирует очередь вызовов: они выполняются один за другим, по порядку.

Сигнатура: `queue(fn, options?)`.

Подробнее: [Очередь событий через `queue`](#очередь-событий-через-queue).

### `dedupe`

Повторный вызов с тем же payload не запускает работу заново, пока идёт первый запуск: он ждёт и получает тот же результат. Когда запуск закончился, ничего не хранится.

Сигнатура: `dedupe(fn, options?)`.

Подробнее: [`dedupe`: общий запуск для одинаковых вызовов](#dedupe-общий-запуск-для-одинаковых-вызовов).

### `distinct`

Вызов, чей payload равен последнему, пропускается и завершается значением `undefined`.

Сигнатура: `distinct(fn, options?)`.

Подробнее: [`distinct`: пропуск повторного payload](#distinct-пропуск-повторного-payload).

### `rateLimit`

В любом окне из `ms` начинается не больше `limit` запусков. Остальные вызовы ждут своей очереди.

Сигнатура: `rateLimit(limit, ms, fn, options?)`.

Подробнее: [`rateLimit`: соблюдение квоты](#ratelimit-соблюдение-квоты).

### `batch`

Собирает payload, пришедшие за окно в `ms`, и вызывает `fn` один раз со всеми ними.

Сигнатура: `batch(ms, fn, options?)`.

Подробнее: [`batch`: отправка нескольких вызовов одним](#batch-отправка-нескольких-вызовов-одним).

### `key`

Параметр каждой политики. Он разделяет state политики по признаку, например по id: вызовы с разными ключами не влияют друг на друга.

Сигнатура: `latest(fn, { key: (payload) => payload.id })`.

Подробнее: [`key`: разделение state по ключу](#key-разделение-state-по-ключу).

Чтобы применить политику к своей функции без шины, см. [`withPolicy`: вызов политики вне шины](#withpolicy-вызов-политики-вне-шины).

## Настройка debounce и throttle

`debounce` и `throttle` принимают два параметра: `leading` и `trailing`. Они решают, какой вызов серии выполнится. `leading` выполняет первый вызов серии сразу. `trailing` выполняет последний вызов в конце серии. Обе функции построены по тому же алгоритму, что в lodash (и patronum), и ведут себя точно так же.

**Throttle** (`throttle(ms, fn)`) выполняет вызов сразу, если до него `ms` ничего не выполнялось, удерживает вызовы, пришедшие в течение `ms`, и выполняет последний из них, когда окно закрывается. При стабильном потоке запуск идёт каждые `ms`.

- `leading` — выполнить первый вызов серии сразу. По умолчанию `true`. При `false` даже первый вызов ждёт конца своего окна.
- `trailing` — выполнить последний удержанный вызов, когда окно закрывается. По умолчанию `true`. При `false` вызовы, сделанные во время окна, отбрасываются.

**Debounce** (`debounce(ms, fn)`) выполняет последний вызов серии после `ms` тишины.

- `trailing` — выполнить последний вызов после `ms` тишины. По умолчанию `true`.
- `leading` — выполнить ещё и первый вызов серии сразу. По умолчанию `false`. Завершающий запуск тогда происходит, только если следуют ещё вызовы.
- `leading: true, trailing: false` — только первый вызов серии.
- Оба `false` — ничего не запускается.

## `key`: разделение state по ключу

`key` даёт каждому ключу своё state. Вызовы с разными ключами не влияют друг на друга. Простаивающие ключи удаляются, поэтому ключей может быть сколько угодно (идентификаторы, URL).

```js
import { createBus } from "nanoeffects";
import { latest, queue } from "nanoeffects/policies";

const bus = createBus();

// один запуск latest на идентификатор пользователя
bus.on(
  "load",
  latest(loadUser, { key: (user) => user.id }),
);

// загрузки одного и того же файла идут одна за другой
bus.on(
  "upload",
  queue(upload, { key: (file) => file.name }),
);
```

## Очередь событий через `queue`

```js
import { createBus } from "nanoeffects";
import { queue } from "nanoeffects/policies";

const bus = createBus();

// queue — один за другим, по порядку
bus.on(
  "save",
  queue(async (draft, { signal }) => {
    await api.save(draft, { signal });
  }),
);

bus.emit("save", draftA); // выполняется сразу
bus.emit("save", draftB); // ждёт draftA, затем выполняется
```

| Параметр | Значение |
| -------- | -------- |
| `concurrency` | сколько вызовов могут идти одновременно (по умолчанию `1`) |
| `limit` | сколько вызовов могут ждать |
| `overflow` | когда очередь полна: `"drop-new"` (по умолчанию) или `"drop-old"` |

Отброшенный вызов завершается значением `undefined`. `queue(fn, { limit: 1, overflow: "drop-old" })` оставляет только последний ожидающий вызов. `limit: 0` не даёт никому ждать.

Каждый вызов возвращает Promise с результатом собственного запуска. Ошибка отклоняет только этот вызов; очередь продолжает работу.

**Прерывание:**

- Ожидающий вызов, чья задача прервана, пропускается и завершается значением `undefined`.
- Когда прерывается выполняющийся вызов, его слот освобождается сразу, а результат отбрасывается.
- Передавайте `signal` в то, что делает `fn`. `fn`, который его игнорирует, может пересечься со следующим запуском.

## `dedupe`: общий запуск для одинаковых вызовов

> **Уровень B или C.** Подходит для чтения, которое несколько частей экрана запускают одновременно.

**Проблема.** Три компонента в одном такте запрашивают пользователя `1`. Без политики это три одинаковых запроса.

**Когда.** Для чтения, которое безопасно повторять: профиль, конфиг, список по id. Для записи используйте [`leading`](prevent-double-submit.md) или [`queue`](#очередь-событий-через-queue): см. правило прерывания ниже.

`dedupe` запускает `fn` для первого вызова. Вызов с тем же ключом, пришедший, пока идёт этот запуск, ждёт его и получает его результат или его ошибку. Когда запуск закончился, `dedupe` его забывает, и следующий вызов запускает `fn` заново. Это не кэш: старое значение он не вернёт никогда.

```js
import { dedupe, withPolicy } from "nanoeffects/policies";

// dedupe — вызовы с одним id делят один запрос
const policy = dedupe((id, { signal }) => api.getUser(id, { signal }));

// withPolicy — обычная функция, поэтому пример показывает результат каждого вызова
const loadUser = withPolicy(policy);

// два вызова, один запрос: оба получают одного пользователя
const [first, second] = await Promise.all([loadUser(1), loadUser(1)]);
```

На шине выглядит так же: `bus.on("user/load", dedupe(handler))`. Чтобы получить результат `emit`, используйте action или job ([Actions](actions.md)).

| Параметр | Значение |
| -------- | -------- |
| `key` | что делает два вызова «одинаковыми». По умолчанию сам payload, сравнивается как ключ `Map`. Объекты не совпадают, пока `key` не скажет как. `key: () => "all"` даёт один общий запуск на все вызовы |

**Прерывание:**

- Вызов, чья задача прервана, завершается значением `undefined`. Остальные продолжают.
- Запуск принадлежит задаче первого вызова. Если эта задача прерывается, пока другие ещё ждут, запуск прерывается и начинается заново со следующим вызовом, поэтому `fn` может выполниться дважды для одного запроса. Для чтения это нормально, для записи — нет.
- Передавайте `signal` в то, что делает `fn`, как для любой политики.

## `distinct`: пропуск повторного payload

> **Уровень B.** Подходит, когда одно и то же значение приходит снова и снова, а повторять работу не нужно.

**Проблема.** Форма сохраняется при каждом изменении. Пользователь набрал букву и стёр её, и тот же текст снова уходит на сервер.

`distinct` сравнивает payload каждого вызова с payload последнего пропущенного вызова. Равный payload пропускается: `fn` не запускается, а вызов завершается значением `undefined`. Политика помнит один payload, но не результат.

```js
import { distinct, withPolicy } from "nanoeffects/policies";

// distinct — запускается, только если текст отличается от последнего пропущенного
const policy = distinct(async (text) => {
  await api.save(text);
});
const save = withPolicy(policy);

await save("hello"); // выполняется
await save("hello"); // пропущен, завершается значением undefined
await save("hello!"); // выполняется: текст изменился
```

| Параметр | Значение |
| -------- | -------- |
| `equals(previous, next)` | говорит, одинаковы ли два payload. По умолчанию `Object.is` |
| `key` | каждый ключ помнит свой payload |

- Payload считается увиденным с момента начала его запуска, поэтому такой же payload, пришедший во время запуска, тоже пропускается.
- Он забывается, когда запуск завершился ошибкой или его задача прервана, поэтому повтор с тем же payload выполнится.
- Память ключа остаётся после запуска. В отличие от других политик, `distinct` не удаляет простаивающие ключи, поэтому давайте `key` значения из ограниченного набора (id формы, а не id запроса).

## `rateLimit`: соблюдение квоты

> **Уровень C.** Подходит, когда API разрешает N запросов за период.

**Проблема.** API геокодирования разрешает 5 запросов в секунду. Список из 40 адресов отправляет 40 запросов сразу, и большинство падает с `429`.

`rateLimit(limit, ms, fn)` разрешает начаться не больше чем `limit` запускам в любом окне из `ms` миллисекунд. Окно скользящее: оно отсчитывается назад от каждого вызова. Вызов сверх лимита ждёт и начинается по порядку, когда самый старый старт выходит из окна.

```js
import { rateLimit, withPolicy } from "nanoeffects/policies";

// rateLimit — за секунду могут начаться 5 запусков, остальные ждут своей очереди
const policy = rateLimit(5, 1000, (address, { signal }) => {
  return api.geocode(address, { signal });
});
const geocode = withPolicy(policy);

const addresses = ["10 Main St", "22 Oak Ave", "5 Pine Rd", "8 Elm St", "3 Lake Dr", "9 Hill Ln"];

// первые пять начинаются сразу, шестой — через секунду
const results = await Promise.all(addresses.map(geocode));
```

| Параметр | Значение |
| -------- | -------- |
| `overflow` | `"wait"` (по умолчанию) держит вызов, пока он не сможет начаться. `"drop"` отбрасывает вызов, который застал окно полным: он завершается значением `undefined` |
| `key` | у каждого ключа своё окно, например по одному на пользователя |

- Политика ограничивает **старты**, а не число одновременных запусков, и не ждёт окончания запуска. Для обоих ограничений напишите `queue(rateLimit(5, 1000, fn), { concurrency: 2 })`: вызов держит свой слот в очереди, пока ждёт окна.
- Вызов, чья задача прервана во время ожидания, выходит из очереди. Прерывание уже начавшегося запуска не возвращает его место в окне: запрос уже отправлен.
- `limit` меньше 1 считается равным 1.

## `batch`: отправка нескольких вызовов одним

> **Уровень C.** Подходит, когда работа дешевле оптом: события для аналитики, строки лога, запрос «дай эти id».

**Проблема.** Страница отправляет событие аналитики на каждый клик, 30 запросов в минуту. Серверу удобнее один запрос со всеми.

`batch(ms, fn)` открывает окно в `ms` на первом вызове и собирает payload, пришедшие за это время. Когда окно закрывается, `fn` запускается один раз с массивом из них, в порядке вызовов. Окно не сдвигается, когда приходят новые вызовы, поэтому постоянный поток отправляется каждые `ms`, а не только когда он затих.

```js
import { batch, withPolicy } from "nanoeffects/policies";

// batch — fn получает массив всего, что пришло за 500 мс
const policy = batch(500, async (events) => {
  await api.sendEvents(events);
});
const track = withPolicy(policy);

track({ name: "open" });
track({ name: "click" }); // один запрос с обоими событиями, через 500 мс после первого
```

| Параметр | Значение |
| -------- | -------- |
| `maxSize` | отправить пакет сразу, когда в нём набралось столько payload |
| `key` | каждый ключ собирает свой пакет, например по одному на пользователя |

- Каждый вызов завершается тем, что `fn` вернул для его пакета: одно и то же значение для всех или одна и та же ошибка. `batch` не делит результат-массив между вызовами.
- Вызов, чья задача прервана, пока пакет собирается, выходит из него и завершается значением `undefined`. Когда вышли все вызовы, ничего не запускается.
- `fn` получает контекст первого вызова, который ещё ждёт. Если эта задача прерывается, пока идёт `fn`, запуск прерывается, и все вызовы этого пакета завершаются значением `undefined`. Запуск не повторяется: часть массового вызова могла уже выполниться.

## `withPolicy`: вызов политики вне шины

**Проблема.** Нужен обработчик ввода с debounce или запрос по принципу «побеждает последний» для вашей собственной функции, но шины в коде нет: DOM-обработчик, callback клика, функция в сервисе. Политике на каждом вызове нужен контекст, поэтому `debounce(300, search)("re")` сам по себе не работает.

**Когда.** Одному полю ввода, кнопке или функции нужна политика и больше ничего из библиотеки. Если шина у вас уже есть, проще `bus.on(event, policy)`. В компоненте React берите [`usePolicy`](react.md#обработчик-с-debounce-между-рендерами): он ещё и сохраняет функцию между рендерами.

`withPolicy` принимает политику и возвращает обычную функцию. Ей не нужны ни шина, ни аргумент с контекстом, и она сохраняет state политики между вызовами.

```js
import { debounce, withPolicy } from "nanoeffects/policies";

const input = document.querySelector("#search");

// debounce — ждёт 300 мс тишины, затем запускает callback
const policy = debounce(300, async (query, { signal }) => {
  const items = await api.search(query, { signal });
  render(items);
});

// withPolicy — обычная функция: без шины и без аргумента с контекстом
const onInput = withPolicy(policy);

input.addEventListener("input", (event) => onInput(event.target.value));

// cancel — отбрасывает ожидающий вызов и прерывает выполняющийся запрос, например при закрытии страницы
window.addEventListener("pagehide", () => onInput.cancel());
```

- У callback та же форма `(payload, ctx)`, что и для шины. `ctx.signal`, `ctx.abort` и `ctx.run` работают. `ctx.emit` и `ctx.on` ничего не делают, потому что шины нет.
- Каждый вызов возвращает Promise с результатом. Вызов, отброшенный политикой, завершается значением `undefined`.
- `cancel()` прерывает каждый вызов, который ещё не закончился. Вызовы после него снова работают.
- Там, где есть `Symbol.dispose`, `using onInput = withPolicy(policy)` вызывает `cancel()` в конце области видимости.
