# Как устроена библиотека

> **[Уровень F](README.md#виды-проектов)**: платформа, SDK или долгоживущее приложение. Сначала прочитайте: [Руководство](guide.md#1-создание-шины-событий).

Всё, что библиотека делает со временем (отмена устаревшего запроса, остановка группы, размонтирование модуля), держится на одной модели: **задача** с одним **сигналом** и задачи, которые следуют за сигналом друг друга. Эта страница объясняет модель. После неё правила [политик](policies.md), [эффектов](effects.md) и [модулей](actions.md) читаются как одно правило, а не как список случаев.

## Модель коротко

- `bus.emit` запускает одну **задачу** на каждый обработчик.
- У каждой задачи свой `AbortController`. Его сигнал — это `ctx.signal`.
- Задача, которую запустила другая задача (`ctx.run`, группа эффекта), **следует** за сигналом родителя: когда родитель прерывается, потомок прерывается с той же причиной.
- Сигнал прерывает кто-то один: политика, размонтированный модуль или ваш код. Работа останавливается только там, куда этот сигнал передали.

## Задача — один запуск обработчика

`bus.emit("search", "re")` вызывает все обработчики `"search"`. Каждый вызов получает свой контекст, `ctx`, и этот контекст и есть задача. В контексте есть событие (`type`, `payload`), сигнал и `abort`, а также методы шины `emit`, `on`, `off` и `run`. Ваши поля из [`context`](context.md) тоже в нём.

Задача — не promise и не поток. Это сигнал и правила: что делать, когда он прерван. Обработчик может быть обычной функцией или `async`; библиотека его не ждёт, а задача заканчивается, когда сигнал больше не нужен.

## У каждой задачи один сигнал

`ctx.signal` — стандартный `AbortSignal`, поэтому всё, что знает сигнал платформы, с ним работает: `fetch`, `addEventListener`, `AbortSignal.any`. Библиотека добавляет только то, чего платформе не хватает:

- `ctx.abort(reason)` прерывает сигнал этой задачи изнутри.
- `onAbort(ctx, callback)` вызывает `callback` один раз, с причиной, когда сигнал прерван, или сразу, если он уже прерван. Возвращает функцию, которая снимает подписку.
- `ctx.emit` и `ctx.on` после прерывания ничего не делают, поэтому отменённый обработчик больше не может обращаться к шине.

## Сигналы образуют дерево

Задача, запущенная из задачи, следует за её сигналом. Такого потомка делают три вещи:

- `ctx.run(fn, payload)` запускает `fn` как дочернюю задачу.
- Группа эффектов (`all`, `allSettled`, `race`, `transaction`) делает по одному потомку на каждую свою функцию. Каждая функция получает `child`: передайте его эффекту или передайте `child.signal` в свой API.
- Эффект, который принимает `ctx` (`retry`, `timeout`, `poll`), слушает его сигнал и останавливается вместе с ним.

```js
import { createBus } from "nanoeffects";
import { all, onAbort } from "nanoeffects/effects";
import { latest } from "nanoeffects/policies";

const bus = createBus();

bus.on(
  "search",
  // latest — новый "search" прерывает сигнал предыдущей задачи
  latest(async (query, ctx) => {
    // onAbort — вызывается, когда эта задача прервана
    onAbort(ctx, () => console.log("search cancelled"));

    // all — два потомка этой задачи; они останавливаются вместе с ней
    const { users, tags } = await all(ctx, {
      users: ({ signal }) => api.users(query, { signal }),
      tags: ({ signal }) => api.tags(query, { signal }),
    });

    render(users, tags);
  }),
);
```

Когда эмитят второй `"search"`, дерево первого выглядит так, и `latest` прерывает его корень:

```text
bus.emit("search", "re")
└─ task: the handler of "search"     ctx.signal   ← aborted by latest
   ├─ group: all                     follows the task
   │  ├─ child: users                { signal } goes to api.users
   │  └─ child: tags                 { signal } goes to api.tags
   └─ run child: ctx.run(...)        follows the task
```

Одно прерывание идёт вниз по всему поддереву с одной причиной. Потомка можно прервать отдельно (проигравший starter у `race`, упавший `all`), а родитель и соседи продолжат работу.

**Задача, запущенная через `ctx.emit`, — потомок в трассировке, но не в дереве сигналов.** Обработчики, которые запускает `ctx.emit("next")`, становятся новыми корнями: прерывание эмитера их не прерывает. Это сделано намеренно, потому что событие — сообщение, а не вызов. Чтобы связать работу обработчика с тем, кто его эмитил, используйте `ctx.run` или `emit` с `signalPlugin`, который принимает `{ signal }` (см. [Сохранение сигнала в обработчике](pass-the-signal.md)).

## Кто прерывает сигнал

| Кто | Когда |
| --- | --- |
| [Политика](policies.md) | `latest` прерывает предыдущий вызов, `debounce` — тот, который заменяет; `cancel()` у `withPolicy` прерывает вызовы, которые не завершились. |
| Группа эффектов | `race` прерывает проигравших, `all` — остальных после ошибки, любая группа — когда прерван её родитель. |
| Модуль | `unmount` прерывает все задачи модуля. |
| `signalPlugin` | Сигнал, переданный в `emit(call, { signal })`, прерывает задачи, которые запускает этот `emit`; переданный в `on` — снимает подписку. |
| Ваш код | `ctx.abort(reason)` или `AbortController`, который вы дали запросу на backend. |

## Что делает прерывание и чего не делает

Прерывание — это просьба, а не остановка: JavaScript не умеет останавливать код снаружи. Библиотека делает следующее:

- Promise эффекта (`retry`, `delay`, `take`, группа) **отклоняется с причиной прерывания**, даже если значение получено в том же тике. Прерванная задача результата не отдаёт.
- `ctx.emit` и `ctx.on` ничего не делают, а подписки, созданные через `ctx.on`, снимаются.
- `rollback` у [`transaction`](effects.md#transaction) всё равно выполняется, потому что прерывание — повод откатить работу. Signal он намеренно не получает.

Остановить то, что игнорирует сигнал, она не может: `fetch` без `signal`, собственный таймер, вызов клиента, который сигнал не принимает. Такая работа дойдёт до конца, а результат отбросят, потому что задача прервана. Поэтому важна страница [Сохранение сигнала в обработчике](pass-the-signal.md): lint-правила и `devPlugin` находят места, где `ctx.signal` потерян.

## Откуда сигнал приходит снаружи

Модель начинается на шине. Сигнал, рождённый в другом месте, присоединяется в нескольких точках:

- [`signalPlugin`](pass-the-signal.md) даёт `emit(call, { signal })`, так что прерывание вызывающего (запрос, сокет, эффект React) прерывает задачи, которые запускает этот `emit`.
- [`fromSignal`](context.md#поле-построенное-из-сигнала-задачи) строит поле `ctx` из сигнала каждой задачи, например HTTP-клиент, который останавливается вместе с ней.
- [`signalFetch`](pass-the-signal.md#привязка-сигнала-один-раз) — это `fetch`, который первым аргументом принимает `ctx`.

## Чего это стоит

- Один `AbortController` на задачу и одна связь с родителем. `unlink` снимает связь, когда задача закончилась, поэтому долгоживущий родитель ничего не хранит от завершённого потомка.
- Один настоящий слушатель `abort` на каждый сигнал, сколько бы подписчиков ни было у `onAbort`. Тысяча подписчиков на одном сигнале — это один слушатель и множество.
- Шина остаётся маленькой (около 1,3 кБ): трассировка, политики и эффекты — отдельные точки входа, которые вы подключаете по необходимости.

## Где смотреть в исходниках

| Часть | Папка | Что в ней |
| --- | --- | --- |
| Шина и задачи | `src/core` | `createBus`, `createTask`, контекст, контракт трассировщика |
| Сигналы | `src/utils` | `onAbort`, `linkedController`, `raceAbort`, таймеры |
| Политики | `src/policies` | `latest`, `queue`, `debounce` и остальные, на одном ядре |
| Эффекты | `src/effects` | `retry`, `timeout`, группы, `transaction` |
| Плагины | `src/signal`, `src/actions`, `src/trace`, `src/dev` | то, что добавляют через `bus.use` |
