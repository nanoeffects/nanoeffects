# Семантика

> **Уровень F.** Сначала прочитайте: [Руководство](guide.md#1-создайте-шину), шаги 1–6.

Гарантии и острые углы. Читайте, когда что-то вас удивило; для старта не обязательно.

## Пять правил, которые нужно знать в первую очередь

1. Обработчик — это `(payload, ctx)`. Используйте `ctx.signal`, `ctx.emit` и `ctx.on`; остальное в `ctx` необязательно.
2. Передавайте `ctx.signal` тому, что вызывает обработчик (`fetch`, клиент), чтобы прерывание останавливало работу.
3. Прерванная задача не выдаёт результата и ничего не отправляет.
4. `emit` синхронный: первая ошибка обработчика выбрасывается, если не задан `onError`.
5. Отклонения async-обработчиков без `onError` не обрабатываются.

Подробности каждого правила и остальное:

- **Прерванная задача не выдаёт результата.** Если задача прерывается до завершения промиса, промис отклоняется с причиной прерывания, даже если значение только что было получено в том же тике. `latest`, `debounce`, `all`, `race`, `take` и остальные следуют этому правилу.
- **`emit` — обычный синхронный цикл** (см. [Ошибки](errors.md)). `ctx.emit` внутри обработчика — тот же вызов: без `onError` ошибка вложенного обработчика выбрасывается в обработчик, который отправил событие; с `onError` она уходит туда, а `ctx.emit` не выбрасывает.
- **Отклонения async-обработчиков** за вас не обрабатываются. Без `onError` это необработанные отклонения, которые по умолчанию завершают процесс Node. Для async-обработчиков используйте `onError`.
- **`leading` снимает блокировку, когда задача прерывается**, а не только когда завершается `fn`. `fn`, который игнорирует сигнал прерывания, может тогда пересечься со следующим запуском — передавайте `ctx.signal` тому, что делает `fn`.
- **Эффекты запускают свою функцию синхронно**, поэтому событие, отправленное сразу после вызова, доходит до `take` внутри неё.
