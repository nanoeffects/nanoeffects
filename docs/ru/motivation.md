# Зачем нужна nanoeffects

> **Уровень A.** Сначала прочитайте: [README](../../README.md).

Эта страница объясняет, зачем существует библиотека и когда её выбирать. Главная причина — вынести бизнес-логику и побочные эффекты из компонентов React, Vue или Svelte и писать их как обычные `async`-функции с отменой, повторами и контекстом для зависимостей. Вторая часть страницы — для SDK, базовых библиотек и оболочек микрофронтендов, где общая зависимость — общий риск. API здесь не объясняется: начните с [Руководства](guide.md). Не уверены, нужна ли вам библиотека вообще? Перейдите к разделу [Когда это не тот инструмент](#когда-это-не-тот-инструмент).

## Главная причина: логика вне UI

Компоненты, в которых лежат запросы, таймеры и гонки, трудно тестировать и легко сломать. Обычное лекарство — сервисы и чистые функции вне UI, и тогда каждому сервису нужно одно и то же: отменять работу, которая больше не нужна, повторять, делиться зависимостями и показывать, что выполнилось и почему.

Привычные инструменты требуют многого: redux-saga пишет эту логику генераторами, а RxJS — потоками и операторами. nanoeffects оставляет обычные `async`-функции и добавляет одну идею — `AbortSignal`. Шина событий — её сердце, но не её ценность: любой эмиттер умеет отправлять события (`nanoevents` весит около 100 байт, а [таких ещё десятки](https://github.com/gajus/sister#similar-libraries)). nanoeffects добавляет отменяемые задачи, политики и эффекты, контекст, который работает как небольшой контейнер зависимостей, действия и модули для группировки фичи и [трассировку](tracing.md) с адаптером для Redux DevTools. Библиотека также ложится на то, что в проекте уже есть: рецепты и небольшие адаптеры для [сторов](stores.md) (Redux Toolkit, Zustand, MobX, Pinia), мост к [RxJS](migrating-from-rxjs.md) и помощники для [React](react.md), [Vue](vue.md) и [Svelte](svelte.md), так что для старта ничего не нужно переписывать.

## Когда ограничение — общая библиотека

Общая библиотека (SDK, базовый пакет, оболочка платформы) загружается множеством приложений. От чего зависит она, от того зависят и приложения. Библиотеки состояния и событий — худший случай, потому что они хранят **внутреннее состояние и идентичность** (стор, контекст, класс). Две копии или две версии таких библиотек не сливаются: они молча перестают видеть друг друга.

Module Federation делает это заметным. Каждый remote может принести свою копию, если все команды не договорятся о `singleton` и диапазоне версий. [Руководство Nx по версиям библиотек](https://nx.dev/docs/kb/manage-library-versions-with-module-federation) перечисляет результат: библиотеки с внутренним состоянием конфликтуют, а отсутствующий в одной версии метод ломает вызывающих, написанных под другую.

Реальные случаи из библиотек, с которыми сравнивали nanoeffects:

| Библиотека | Что идёт не так | Источник |
| ---------- | --------------- | -------- |
| Redux, React Redux | Общая библиотека компонентов использует `react-redux`. Каждый микрофронтенд должен использовать ту же версию этой библиотеки, иначе `react-redux` «странно ломается». | [react-redux#1949](https://github.com/reduxjs/react-redux/issues/1949) |
| Redux | Стор доступен только под `Provider`. Каждому под-приложению нужен свой провайдер, а второй нельзя создавать при внедрении модуля. Редьюсеры, продублированные между хостом и модулем, усугубляют ситуацию. | [Redux on Module Federation](https://dev.to/manomano-tech-team/how-to-work-with-redux-on-module-federation-13gm) |
| Effector | Библиотека, использующая `effector-react/scope` и собранная в другой проект, получает два экземпляра. Её `Provider` не виден `useStore` приложения: «no scope found». | [effector#727](https://github.com/effector/effector/issues/727) |
| RxJS | Две копии дают два класса `Observable`. Типы одной версии не подходят другой, а операторы, добавленные в одну копию, отсутствуют в другой. Совет — «одна версия в `node_modules`». | [RxJS#2984](https://github.com/ReactiveX/rxjs/issues/2984), [neo4j-javascript-driver#978](https://github.com/neo4j/neo4j-javascript-driver/issues/978) |

Библиотека, которая **не** является общим синглтоном, так сломаться не может. У nanoeffects нет зависимостей и нет состояния уровня модуля: шина — это объект, который вы создаёте. Две копии или две версии пакета на одной странице — это две независимые шины. Ничего не регистрируется глобально, `Provider` не нужен, и хост-приложению не приходится выбирать для вас версию.

## Почему не альтернативы

| Вариант | Почему не подошёл |
| ------- | ----------------- |
| Redux (с сагами) | Стор и провайдер, общие для всех потребителей, то есть риск, описанный выше. У `redux-saga` к тому же нет дешёвого способа получить ответ на событие: эффекты общаются через стор. |
| Effector | Граф с глобальной идентичностью. Несовпадение версии или scope между SDK и приложением затрагивает всю инфраструктуру. |
| Zustand | Хорошее состояние, но это стор, а не способ запускать и отменять работу. Он — естественное место для состояния рядом с nanoeffects: см. [Сторы](stores.md). |
| RxJS | Гибкий, но изучение его экосистемы (операторы, subjects, schedulers) — высокий порог входа для каждого разработчика, который касается SDK. Пакет к тому же не маленький: [Bundlephobia](https://bundlephobia.com/package/rxjs) сообщает 17,3 кБ в минифицированном и сжатом gzip виде для 7.8.2. |

## Что библиотека делает вместо этого

- **Нет зависимостей и глобального состояния.** Её безопасно поставлять внутри SDK рядом с тем, что запускает хост-приложение. Запись `singleton` в конфиге Module Federation не нужна.
- **Достаточно мала для жёсткого бюджета.** SDK часто получают несколько килобайт на весь сторонний код. `createBus` весит около 1,4 кБ в gzip (1,3 кБ в brotli); политики, эффекты и действия — отдельные точки входа, которые вы импортируете, только когда нужно. См. [Точки входа пакета](package.md).
- **Сначала просто.** `on` и `emit` — вся модель. Отмена, повторы и остальное — обычные функции поверх. [Руководство](guide.md) и [Переход с redux-saga](migrating-from-saga.md) сопоставляют знакомые имена.
- **`emit` может вернуть ответ.** [Действие с обработчиком](actions.md) возвращает результат, поэтому один модуль может спросить другой и дождаться ответа. Одни события так не умеют, и именно этого больше всего не хватало вариантам на Redux.
- **Легко отлаживать.** Событийный код трудно читать: вы видите эффект, а не событие, которое его вызвало. Каждая задача знает своего родителя, поэтому [трассировка](tracing.md) показывает цепочку событий, с логгерами для консоли, панели Performance и Redux DevTools.

## Когда это не тот инструмент

Небольшому приложению с одним-двумя запросами библиотека не нужна: `fetch` в обработчике события годится, пока не появится первая гонка. nanoeffects не хранит состояние. Если нужен стор, оставьте Redux, Zustand или Effector и пусть шина ведёт async-работу: [Сторы](stores.md). Если потоки у вас уже везде, оставьте RxJS: [nanoeffects рядом с RxJS](migrating-from-rxjs.md).
